# ADR 0002 — One authoritative Hub, not multi-master sync

- **状态**：已采纳（issue #1 的 PR1–PR5）
- **日期**：2026-11-05
- **取代**：无。补充 [ADR 0001](./0001-widget-decoupled-from-source.md)（Widget 与 Source 解耦），
  二者正交：0001 说布局是用户数据，0002 说这份数据只在一个地方被写。

## 背景

用户有多台设备，每台独立跑 DSH，都装了本插件。期望是：任一设备记下的 Todo / Note / Board 状态，
其它设备能读到同一份；记录本身**不启动模型**；下次真人对话时 Agent 能拿到最新个人状态。

朴素做法是每台设备都写本地存储域，再想办法互相同步。这条路要面对 CRDT、向量时钟、离线多主冲突、
消息队列——而这些正是个人使用场景里不需要的成本。

## 决定

**一份权威数据，放在一个 Hub 上；其它设备是只读代理 + 写入转发。**

- `standalone`（默认）：本机就是权威，零行为变化。
- `hub`：本机是权威，并对外提供受令牌保护的 `/sooyo/sync/v1/*`。
- `client`：不打开权威存储域；每次读都是 Hub 读，每次写都是 Hub 命令。

写入只有一个入口（`core/commands.js` 的 `execute`），它做四件事：白名单、严格校验、计划成具体写步骤、
经日志执行并推进 revision。

## 理由

1. **冲突变成可回答的问题，而不是要发明的算法。** 单写者 + 每记录 `revision` + 可选前置条件，
   冲突就是 `409` 加当前记录。用户看到的是一条"这条改过了，刷新一下"，而不是静默丢失。
2. **`client` 没有本地权威副本。** 一份会分叉的第二副本比没有副本更糟。所以 `client` 缺配置时**报错**，
   而不是起一个空库（这也让 AC-05 可以直接成立）。
3. **一次抓取。** 只有权威抓信源。两台设备同时轮询同一个 feed 既是浪费也是对站点的不礼貌（AC-07）。
4. **后台工作有唯一归属。** 定时审阅只有 Hub 做，所以同一件事不会被建议两遍。
5. **可以替换后端而不动界面。** 将来真要独立部署云端 API，替换的是 `SooyoService` 的实现，
   UI 与 Agent 的工具契约不变。

## 代价（明确接受）

- **Hub 挂了，所有设备的写入都不可用。** 读可以继续用最后一次成功的缓存，但会标 `stale`。
  这是 MVP 取舍，不是疏忽。
- **不在同一局域网/私网内就得自己解决暴露问题。** 默认 `allowLoopbackOnly: true`；
  要跨网就上 Tailscale 或带 TLS 的反代，并且**只开 `/sooyo/sync/v1/*`**，不要暴露整个 DSH 管理界面。
- **没有实时推送。** 可见页面 15–30s 低频条件请求，写入成功后刷新。没有 SSE/WebSocket。
- **没有跨表事务。** 存储域只保证单记录原子。多步命令靠日志 + 启动恢复，而不是假装有事务。
- **两个 Host 不能同时以 hub 身份写同一份数据。** 没有跨进程修订协议。

## 被否决的替代方案

| 方案 | 否决原因 |
|---|---|
| 多主双向同步 / CRDT | 个人场景不需要离线并发写；复杂度远高于收益 |
| 每台设备独立库 + 定时合并 | 合并规则无法正确处理"两台都改了同一条"；最终仍要人工介入 |
| 用 OpenViking 当 Todo 权威库 | OpenViking 管长期记忆/资源/技能，不管"这条 Task 今天完成了没有"。职责混用会让两者都不准 |
| 独立 Node/Hono 服务 + 独立 DB | 多一个要部署、要备份、要保活的东西；插件本身就跑在 DSH 里 |
| 直接把整个 DSH Web Server 暴露公网 | 那把管理界面也暴露了；同步 API 是唯一需要跨网面的东西 |
